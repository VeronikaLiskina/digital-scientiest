# Цифровой учёный

Веб-приложение для хранения и обработки научных публикаций, семантического
поиска и ответов на вопросы по загруженным материалам. Ассистент работает по
RAG-подходу: сначала находит подходящие фрагменты публикаций, проверяет их
релевантность и только затем передаёт контекст языковой модели.

## Возможности

- загрузка одной или нескольких PDF-публикаций;
- извлечение текста и метаданных, OCR для сканированных страниц;
- автоматическое разбиение текста на чанки и построение embeddings;
- каталог публикаций, авторов, тем и ключевых слов;
- семантический и полнотекстовый поиск;
- RAG-ассистент с точными ссылками на использованные фрагменты;
- автоматический поиск между русскими и английскими публикациями;
- генерация через Groq API или другой совместимый облачный API;
- очередь фоновой обработки PDF и журнал ошибок;
- автоматические тесты API, поиска, обработки PDF и логики ассистента.

## Как устроен проект

```mermaid
flowchart LR
    UI[React-интерфейс] --> API[FastAPI]
    API --> DB[(PostgreSQL + pgvector)]
    API --> REDIS[(Redis)]
    REDIS --> WORKER[Celery worker]
    WORKER --> PDF[PDF / OCR / чанки / embeddings]
    PDF --> DB

    API --> SEARCH[Vector search + FTS + RRF]
    SEARCH --> GATE[Relevance gate]
    GATE --> RERANK[BGE reranker]
    RERANK --> LLM[Groq / Cloud API]
    LLM --> UI
```

Код разделён по ответственности: `api` принимает HTTP-запросы,
`repositories` работают с базой, а `services` реализуют процессы приложения.
Например, `AssistantRetrievalService` полностью ведёт конвейер поиска, а
`PdfStorageService` — проверку, дедупликацию и сохранение PDF. Зависимости этих
сервисов передаются снаружи, поэтому отдельные этапы можно тестировать и менять
без переписывания API. Общие поля frontend-форм и чистые функции обработки
данных также вынесены из страниц в `components` и `utils`.

## Быстрый запуск

### Требования

- Docker Desktop с Docker Compose;
- доступ в интернет и Groq API key.

### 1. Подготовьте настройки

PowerShell:

```powershell
Copy-Item .env.example .env
```

Bash:

```bash
cp .env.example .env
```

Реальный `GROQ_API_KEY` храните только в `.env`. Этот файл исключён из Git.

### 2. Подключите модель по API

В `.env` оставьте `LLM_PROVIDER=groq`, укажите свой `GROQ_API_KEY` и
`GROQ_MODEL=openai/gpt-oss-120b`. Большая языковая модель выполняется на стороне
провайдера. Для локального резерва ассистента также запустите Ollama
с установленной моделью, указанной в `OLLAMA_MODEL`.

### 3. Запустите приложение

```powershell
docker compose up -d --build
docker compose exec backend alembic upgrade head
```

После запуска доступны:

- пользовательский интерфейс — <http://localhost:5173>;
- ассистент — <http://localhost:5173/assistant>;
- административная часть — <http://localhost:5173/admin>;
- API — <http://localhost:8000>;
- Swagger UI — <http://localhost:8000/docs>;
- проверка состояния — <http://localhost:8000/health>.

Проверить контейнеры и логи:

```powershell
docker compose ps
docker compose logs -f backend celery-worker
```

Остановить приложение без удаления базы:

```powershell
docker compose down
```

> `docker compose down -v` удаляет тома PostgreSQL и Redis вместе с данными.

## Как работает AI-ассистент

Для каждого вопроса выполняется следующий конвейер:

1. `multilingual-e5-base` строит embedding вопроса.
2. pgvector возвращает до 50 семантических кандидатов, PostgreSQL FTS — до
   50 лексических кандидатов.
3. Reciprocal Rank Fusion (`RRF_K=60`) объединяет результаты и оставляет до
   30 чанков.
4. Relevance gate отбрасывает фрагменты без достаточных текстовых или
   семантических признаков.
5. Если первый поиск слабый, вопрос автоматически переводится на другой язык
   и выполняется дополнительный поиск. Исходные и переведённые кандидаты
   объединяются и очищаются от дубликатов. При сильном первом результате
   повторный поиск пропускается, если среди кандидатов нет фрагментов на другом
   языке. При смешанном языковом составе перевод выполняется даже при нескольких
   предварительных совпадениях. Если cross-encoder затем оставляет меньше
   двух фрагментов, двуязычный поиск всё же выполняется: предварительные
   совпадения могут оказаться слабыми.
6. Cross-encoder `bge-reranker-v2-m3` один раз переоценивает общий список пар
   «вопрос — фрагмент». В итоговый контекст попадает не более 6 чанков с
   оценкой не ниже `0.5`.
7. LLM получает только проверенные фрагменты. Ответ проходит валидацию языка,
   JSON-структуры и ссылок на реально использованные `chunk_id`.

В интерфейсе доступны три режима:

- **Авто**: подбор по каталогу и ответы по найденным публикациям; приветствия,
  явные разговорные запросы и продолжения свободного диалога обрабатываются
  напрямую через API. Если источников нет или они не содержат ответа,
  используется отдельная ветка общих знаний.
- **По публикациям**: только каталог и подтверждённые фрагменты. При недостатке
  сведений ассистент сообщает об этом и не заменяет данные архива общими знаниями.
- **Свободный диалог**: разговор, объяснения, программирование и творческие
  задачи напрямую через API без загрузки поисковых моделей.

В «Авто» явная просьба ответить именно по загруженным статьям также требует
доказательств из архива. Ответы из общих знаний помечаются «Свободный диалог ·
Общие знания модели», имеют `answer_origin=external` и не получают ссылок на
публикации. История диалога сохраняется. Подсчёт и подбор публикаций из каталога
остаются точными запросами к базе во всех режимах. Режим передаётся как `mode`
в `/assistant/ask` и `/assistant/chats/{id}/messages`, по умолчанию `auto`.

Запросы на подбор публикаций обрабатываются отдельно, прямо в базе, без LLM
и загрузки моделей поиска. Поддерживаются тема, автор, год/диапазон лет, язык,
тип публикации и их сочетания, например:

- «Какие публикации есть по магнитизму?»;
- «Подбери статьи по ботанике автора Иванова за 2020–2024 годы на русском»;
- «Покажи обзоры на английском языке»;
- «Сколько публикаций по магматизму?».

Название или непрерывный фрагмент названия также проверяется в каталоге до
перехода к общим знаниям во всех режимах. Например, «МЕЛОВАЯ СИСТЕМА РОССИИ»
и «Покажи статью «Меловая система России»» возвращают настоящую карточку
публикации, ссылку и выдержку из обработанного текста. Регистр и знаки
препинания не влияют на совпадение; слова не заменяются похожими.
Продолжение «О чём она?» сохраняет найденное название. Это поиск в базе,
без генерации описания моделью.

Разбор названия общий для статей, сборников, книг, документов и других жанров:
например, «Найди сборник «Меловая система России и ближнего зарубежья»».
Жанр карточки не ограничивает поиск по явно указанному названию. Вопросы
о содержании документа в кавычках направляются в RAG с ограничением по его ID.
Для уточнений в чате ID берутся из сохранённых карточек и источников предыдущего
ответа; ограничение применяется и к векторному, и к полнотекстовому поиску до
ранжирования. Запросы «Какие методы описаны в загруженных статьях?» обрабатываются
как вопросы по содержанию, а не как просьба вывести весь каталог.

Тематический подбор ищет по названиям, темам, ключевым словам и обработанному
тексту с учётом форм слов. Совпадения в названиях и метаданных выводятся выше
упоминаний в тексте. Для магнитизма, палеомагнетизма и магматизма предусмотрены
связанные русские и английские термины; это не универсальный перевод всех тем.
Явно помеченные разделы литературы исключены из текстовых совпадений.
Условия по разным параметрам применяются вместе. Вопрос «А о чём они?» сохраняет
фильтры предыдущего подбора. Также поддерживаются «А только до 2010 года?»,
«А на английском?», «Сколько их?», вежливые просьбы и поиск вида
`Find publications about paleomagnetism`. Научные уточнения используют
предыдущие вопросы пользователя для поиска, а факты — из заново найденных
фрагментов. Обычные научные вопросы продолжают обрабатываться
через RAG и выбранный API.

Оценки cross-encoder для одинаковых пар «вопрос — текст» хранятся в ограниченном
кэше (256 пар). Результаты поиска не кэшируются: добавленные публикации участвуют
в следующем запросе, изменённый текст фрагмента получает новую оценку.

Векторы последних 256 поисковых запросов также переиспользуются. Успешный
перевод одинакового поискового вопроса хранится до 10 минут (не более 128
запросов, отдельно для языка и выбранного API). Готовые ответы не кэшируются.

## Выбор LLM-провайдера

Основной провайдер задаётся в `.env` через `LLM_PROVIDER`: `groq` или `api`.
Локальный резерв ассистента включается отдельно параметром
`LLM_LOCAL_FALLBACK_ENABLED`; штатные запросы остаются в основном API.

| Режим | Поведение | Особенности |
|---|---|---|
| `groq` | Основные запросы идут через Groq API | При сбое возможен включённый локальный резерв |
| `api` | Запросы идут в указанный Chat Completions API | Адрес, ключ и модель задаются в `.env` |

### Только Groq

```env
LLM_PROVIDER=groq
GROQ_API_KEY=gsk_...
GROQ_MODEL=openai/gpt-oss-120b
GROQ_REASONING_EFFORT=medium
GROQ_MAX_COMPLETION_TOKENS=4096
```

Проверить ключ до переключения основного backend:

```powershell
docker compose run --rm -e LLM_PROVIDER=groq backend `
  python -m scripts.check_groq_connection
```

### Переход на платную модель

Для платного доступа в том же Groq код менять не требуется: настройте тариф
в аккаунте провайдера, при необходимости замените `GROQ_API_KEY` и `GROQ_MODEL`.
Для другого сервиса с совместимым Chat Completions API:

```env
LLM_PROVIDER=api
LLM_API_BASE_URL=https://api.provider.example/v1
LLM_API_KEY=your-key
LLM_API_MODEL=your-model
LLM_API_TIMEOUT_SECONDS=120
LLM_API_MAX_COMPLETION_TOKENS=4096
```

Замените пример адреса на адрес провайдера, включая префикс API; путь
`/chat/completions` приложение добавляет само. Модель должна поддерживать
`max_completion_tokens`, структурированные ответы `json_schema` и режим
`json_object` для метаданных PDF. Параметры reasoning Groq другому сервису
не передаются. Совместимость текущего Groq описана в
[документации провайдера](https://console.groq.com/docs/openai).

После изменения `.env` пересоздайте backend и worker:

```powershell
docker compose up -d --force-recreate backend celery-worker
```

### Локальная резервная модель

Основная генерация остаётся через API. При `LLM_LOCAL_FALLBACK_ENABLED=true`
ассистент переключается на Ollama после ошибки API (включая 403/429), пустого
или некорректного ответа, либо превышения 30 секунд ожидания. Если ответ API
дважды не прошёл проверку структуры/ссылок, локальный ответ проходит те же проверки.
При недостатке сведений в источниках модель не меняется ради получения догадки.

По умолчанию используется уже установленная `gemma4:12b`. Ollama вызывается
только при сбое API, без параллельного запуска двух моделей. `OLLAMA_KEEP_ALIVE=0`
выгружает модель после запроса; `OLLAMA_NUM_THREAD=2` ограничивает потоки CPU.
`OLLAMA_USE_MMAP=true` и `OLLAMA_NUM_BATCH=128` уменьшают пик памяти при загрузке
вместе с моделями поиска, что существенно для Windows с ограниченной RAM.
После сбоя обращения к API приостанавливаются на 60 секунд, затем API снова
проверяется новым запросом. Каталог не требует ни одной модели. AI-извлечение
метаданных PDF продолжает использовать основной API без локального резерва.

В Docker адрес Ollama — `http://host.docker.internal:11434`, в локальном запуске
backend на Windows укажите `http://localhost:11434`. Проверьте `ollama list`;
приложение не скачивает отсутствующую модель. На другом ПК Ollama и модель
нужно установить отдельно. Для отключения резерва задайте
`LLM_LOCAL_FALLBACK_ENABLED=false`.

Параметры протокола: [Ollama Chat API](https://docs.ollama.com/api/chat).

### Приватность

Выбранный API получает вопрос, системный prompt и выбранные RAG-фрагменты.
Browser search, code execution и другие внешние tools в проекте не включены.

AI-анализ метаданных PDF использует тот же выбранный API и передаёт ему текст
для извлечения метаданных. Embeddings и reranker остаются локальными: поиск и
обработка PDF по-прежнему используют ресурсы ПК. При включённом резерве большая
локальная модель загружается только при сбое API и получает то же задание.
При штатном ответе API локальная генерация не запускается.

## Обработка публикаций

После загрузки PDF система:

1. проверяет тип, размер и хеш файла;
2. извлекает метаданные и предлагает совпадения из справочников;
3. отправляет подтверждённую публикацию в Celery;
4. извлекает текст, при необходимости запускает OCR;
5. строит смысловые чанки и embeddings;
6. сохраняет результаты и статус обработки в PostgreSQL.

В очередь передаётся только `source_file_id`. Сам PDF читается worker из общего
каталога `backend/uploads`. Redis используется как брокер задач, а состояние и
ошибки сохраняются в PostgreSQL. Celery Beat проекту не требуется.

Ограничения массовой загрузки: не более 20 PDF за запрос, до 50 МБ на один файл
и до 300 МБ на пакет.

OCR применяется уже при автозаполнении карточки — для нового файла, повторного
извлечения из сохранённого PDF и массового импорта. Повреждённый текстовый слой
(нечитаемые символы, сломанная кодировка, смешение кириллицы с латиницей)
перечитывается Tesseract со страницы при 300 dpi. Для английских сканов при
необходимости выполняется проход только с английским языком. Если основные
поля не найдены, первые две страницы дополнительно проверяются через OCR.

Название, полученное распознаванием, имеет источник `ocr`, среднюю уверенность
и предупреждение о ручной проверке. Нечитаемые значения не подставляются в
название, авторов, ключевые слова и темы. Распознавание выполняется локально
установленным в Docker Tesseract с языками `rus` и `eng`, по одной странице
одновременно; отдельный API или большая языковая модель для OCR не нужны.

`PDF_OCR_CACHE_ENABLED=true` включает общий для API и worker кэш распознанных
страниц в уже используемом Redis. Он привязан к SHA-256 содержимого PDF,
номеру страницы и настройкам OCR, поэтому временный файл предпросмотра и
сохранённая копия используют одно распознавание. Изменённый PDF распознаётся
заново. Кэш ограничен 256 страницами по 128 КиБ, удаляется через сутки без
записи; ошибки и нечитаемый текст не сохраняются. Недоступность кэша не мешает
извлечению. Первое распознавание и построение поискового индекса по-прежнему
занимают время.

При выборе названия учитываются координаты строк и размер шрифта; для сканов
используются координаты слов Tesseract. Колонтитулы, логотипы и названия журналов
отбрасываются. Уверенный заголовок со страницы имеет приоритет над именем файла.
Сначала читаются три страницы; поиск расширяется, если название не найдено.

Авторский блок Keywords извлекается отдельно от подбора терминов по аннотации
и названию. Поле `keywords_source` в предпросмотре содержит `explicit`,
`suggested` или `none`; интерфейс отмечает предложения системы. Изотопные
обозначения и географические названия сохраняются, номера страниц исключаются.
Название, предложенное API, принимается только при наличии в тексте PDF.

Английские имена сопоставляются с русским справочником по транслитерации фамилии
и явно указанным инициалам. Совпавшие авторы отмечаются существующими ID;
новые проверенные имена создаются при сохранении карточки. Надстрочные индексы
организаций убираются по разметке PDF. Неоднозначные совпадения и неизвестные
имена из OCR остаются на ручную проверку. Авторы из оглавлений не назначаются
авторам отдельной статьи. В массовом импорте сохранённые строки показывают
актуальных авторов публикации из БД. Для этого каталога Иванов А.В. обязательно
привязывается при создании и изменении публикаций; при запуске восстанавливаются
недостающие связи существующих записей.

## Настройки поиска

Основные переменные находятся в `.env.example`.

| Переменная | Значение по умолчанию | Назначение |
|---|---:|---|
| `EMBEDDING_MODEL_NAME` | `intfloat/multilingual-e5-base` | Модель embeddings |
| `RERANKER_MODEL_NAME` | `BAAI/bge-reranker-v2-m3` | Cross-encoder reranker |
| `RERANKER_MAX_LENGTH` | `768` | Максимальная длина пары для reranker |
| `RERANKER_MIN_SCORE` | `0.5` | Минимальная оценка релевантности |
| `RERANKER_TOP_K` | `6` | Максимум чанков в RAG-контексте |

После первой установки embedding- и reranker-модели скачиваются в общий Docker
том `huggingface_cache`. Поэтому первый содержательный запрос может быть заметно
дольше последующих.

### Смена embedding-модели

После изменения `EMBEDDING_MODEL_NAME` необходимо перестроить векторы всех
чанков:

```powershell
docker compose exec backend python -m app.scripts.rebuild_embeddings
```

Скрипт удаляет векторы другой модели, поэтому поиск не смешивает embeddings от
разных моделей. При смене только reranker перестраивать embeddings не нужно.

## Проверка retrieval на своём наборе

Для повторяемой проверки работающего приложения на текущем архиве:

```powershell
.\.venv\Scripts\python.exe backend/scripts/evaluate_assistant.py `
  --output exports/assistant-catalog.json

.\.venv\Scripts\python.exe backend/scripts/evaluate_assistant.py `
  --include-generation --output exports/assistant-full.json
```

Первый вариант проверяет только каталог. Второй отправляет вопросы и найденные
фрагменты в выбранный API. Сценарии лежат в `backend/evaluation/assistant_cases.json`.
Проверяются факты, ожидаемые публикации, фильтры и согласованность ссылок;
это не автоматическая экспертиза научной достоверности каждого предложения.
Временные чаты проверки удаляются, публикации не изменяются. После добавления
новых материалов сохраните новый отчёт и добавьте вопросы по новым публикациям.

Отдельный набор для свободного диалога, памяти разговора и переключения режимов:

```powershell
.\.venv\Scripts\python.exe backend/scripts/evaluate_assistant.py `
  --dataset backend/evaluation/conversation_cases.json --include-generation `
  --output exports/assistant-conversation.json
```

Проверка готовности к переносу без скачивания моделей:

```powershell
docker compose exec -T backend python -m scripts.check_assistant_readiness --check-api
```

Она проверяет обработку публикаций, совместимость эмбеддингов, наличие PDF,
весов поисковых моделей в кэше, воркера и доступ к выбранному API. С ключом
`--check-api` наружу уходит только короткий синтетический тест подключения.
Порядок переноса описан в [docs/institute-installation.md](docs/institute-installation.md).

Диагностический скрипт может отдельно измерить vector search, FTS, RRF,
relevance gate и reranker. Путь к проверенному JSON-набору передаётся явно:

```powershell
Set-Location backend
..\.venv\Scripts\python.exe -m scripts.evaluate_retrieval `
  --dataset C:\path\to\retrieval_dataset.json
```

Для быстрого baseline без reranker:

```powershell
..\.venv\Scripts\python.exe -m scripts.evaluate_retrieval `
  --dataset C:\path\to\retrieval_dataset.json --skip-reranker
```

## Частые проблемы

### Ассистент не подключается к API

Проверьте интернет, `LLM_PROVIDER`, ключ и имя модели. Для Groq:

```powershell
docker compose run --rm backend python -m scripts.check_groq_connection
```

При включённом локальном резерве ошибка API, включая исчерпание квоты,
переключает ассистента на Ollama. Если резерв тоже недоступен, интерфейс
показывает общую ошибку двух моделей. Если резерв отключён, показывается
исходная ошибка API.

### Первый вопрос отвечает очень долго

При первом запросе загружаются embedding-модель и reranker. Повторный
запрос обычно быстрее. Посмотреть происходящее можно командой:

```powershell
docker compose logs -f backend
```

### После смены `.env` ничего не изменилось

Пересоздайте контейнер:

```powershell
docker compose up -d --force-recreate backend celery-worker
```

### База не соответствует текущему коду

Примените все миграции:

```powershell
docker compose exec backend alembic upgrade head
```

### PDF остаётся в очереди

Проверьте Redis и worker:

```powershell
docker compose ps redis celery-worker
docker compose logs --tail 200 celery-worker
```
